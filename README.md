# ima-kb-qa-eval

**知识库问答质量评测工作台**：50 条可溯源金标问答 · 规则 + LLM-as-judge 双层评分 · badcase 三层归因（检索层 / 生成层 / 数据层）· Streamlit 看板。

> 这个仓库的主体不是"又一个 RAG 应用"，而是 **RAG 应用的效果评测体系**——怎么量化一个知识库问答产品好不好、错了归因到哪一层、结论怎么变成产品动作。

## 为什么做这个

知识库问答类产品（评测对象为 [ima](https://ima.qq.com)，腾讯智能工作台）都有一个结构性问题：**问答质量对用户是黑盒**。

- 用户不知道答案基于哪篇文档、这篇可信吗、库里有没有冲突；
- 答错没有反馈出口，错误被默默接受或默默流失；
- 库越用越厚，旧内容不会自动退休。

本项目先用 20 篇真实语料重度使用产品、记录 24 条 badcase，再围绕四个高频错误场景（错源高排 / 过期信息 / 库外问题 / 细节埋深）构建评测集，最终把"质量黑盒"拆成**可测量、可归因、可行动**的三层结构。

## 它是什么

```
corpus/（20 篇语料）
   │
   ▼
┌─────────────────────── RAG 复现 pipeline（手写，零框架）───────────────────────┐
│  解析 → 切块（标题切节+滑窗） → 混元 embedding（997 chunks） → cosine top-k → 生成 │
└──────────────────────────────────────────────────────────────────────────────┘
   │
   ▼
┌────────────────────────── 双层评分器 ──────────────────────────┐
│ 规则层（自动，零成本）：检索命中率 / 拒答准确率 / 端到端延迟        │
│ 裁判层（LLM-as-judge × 3 次取多数）：忠实度 / 正确性 / 完整性      │
└────────────────────────────────────────────────────────────────┘
   │
   ▼
┌────────────────────── 三层归因决策树 + 人工仲裁 ─────────────────────┐
│ 检索层（没召回/弱命中）→ 调切块与排序                                 │
│ 生成层（有据答错/错误拒答）→ 调 prompt / 反馈闭环                     │
│ 数据层（库本身脏）→ 产品侧知识库健康度  ★ 只有 PM 会得出的归因结论    │
└────────────────────────────────────────────────────────────────────┘
   │
   ▼
Streamlit 看板：总分 / 分题型错误率 / 归因分布 / badcase 按层筛选
```

## 结果速览

| 指标 | 结果 |
|---|---|
| 端到端正确率 | **82%**（错误 9/50，fatal 口径） |
| 检索命中率（top-3，文档级） | 87.5% |
| 拒答准确率（库外问题） | **100%**（10/10） |
| 事实正确率 | 67.6% correct / 14.7% partial |
| 完整性 | 41.2% complete（最大短板） |
| 端到端延迟 | 均值 14.9s / p90 25.7s |
| 分题型错误率 | multi_doc **60%** > reasoning 20% > fact 15% > refusal 0% |

**badcase 三层归因（人工仲裁后）**：检索层 44% ｜ 生成层 44% ｜ 数据层 11%（覆盖 9/9 = 100%）

> 数据层错误看起来少，是因为它需要"过期文档高位排序 + 生成层采信"联合失败才爆发——这套评测体系能把机制完整暴露出来。数据层错误调模型解决不了，只能靠产品机制让用户治理知识库（冲突检测、过期降权、信源权威度标注）。

完整分析见 **[docs/D7_评测报告.md](docs/D7_评测报告.md)**，对应的产品提案见 **[docs/D7_一页纸提案.md](docs/D7_一页纸提案.md)**。

## 快速开始

```bash
# 依赖（Python 3.13）
pip install openai numpy pypdf streamlit

# 配置混元 API key（环境变量，切勿写进代码或提交）
export HUNYUAN_API_KEY=sk-xxx        # Windows: set / $env: 方式均可

# ① 建向量索引（增量缓存，语料不变不重算）
python rag_pipeline.py build

# ② 单条问答试跑
python rag_pipeline.py ask "ima 是什么时候上线的？"

# ③ 全量跑批 50 条 + 双层评分 + 三层自动归因（约 24 分钟，费用 < 10 元）
python run_eval.py run               # 支持 --limit N 冒烟 / --fresh 重跑 / checkpoint 断点续跑

# ④ 人工复核与仲裁（可选但推荐）
python run_eval.py review            # 导出复核清单 CSV
python run_eval.py arbitrate         # 应用人工仲裁，导出最终归因结果

# ⑤ 启动评测看板
streamlit run dashboard.py
```

不想跑批？仓库自带全量结果（`d5_results.json`），clone 后直接 `streamlit run dashboard.py` 就能看板。

### 可配置项（环境变量）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `HUNYUAN_API_KEY` | （必填） | 混元 TokenHub API key |
| `RAG_TOP_K` | 8 | 检索条数 |
| `RAG_CHUNK_SIZE` / `RAG_CHUNK_OVERLAP` | 600 / 120 | 切块大小与滑窗重叠 |
| `LLM_MODEL` / `EMBED_MODEL` | hy3 / kinfra-text-embedding-0.6b | 生成与向量化模型 |
| `LLM_BASE_URL` | TokenHub 官方地址 | OpenAI 兼容网关 |

## 方法论

1. **评测集长在真实使用上**：19/50 条直接改造自重度使用产品的实测 badcase；评测前用 `trap_note` 写好"预期会怎么错"，跑批后按此对照归因——避免事后编故事；
2. **双层评分，成本与噪声双控**：规则指标全自动零成本；模型指标按题裁剪考核维度，每指标跑 3 次取多数（实测裁判分歧率 ~4%，majority 无一翻转）；
3. **三层归因，指向不同的解法**：检索层错误调切块/排序，生成层错误调 prompt/反馈闭环，**数据层错误只能靠产品机制治理知识库**——同一句"答错了"，三层归因给出三种完全不同的行动；
4. **人机协同终判**：自动归因树误判率 22%（9 条错误中 2 条被人工改判），这不是缺陷而是证据——全自动归因负责规模化初判，人工仲裁负责终判与口径修正。

构建过程中踩过的坑（裁判证据面 ≠ 被测证据面、文档级命中率高估检索质量等）记录在 [docs/D7_评测报告.md](docs/D7_评测报告.md) §6。

## 声明

- 本仓库基于**复现架构**评测（被测产品的 MCP 接口不提供问答 API，端到端评测无法在其侧自动化），结论用于方法论演示，**不构成对 ima 真实质量的定量指控**；复现架构会系统性低估数据层错误频率（详见评测报告 §5.5）；
- 裁判与被测模型同为混元 hy3，自我增强偏差经多数投票缓解但未消除；金标 100% 可溯源到文档原文，全部错误样本经人工复核；
- 数据截至 2026-08-31，涉及"最新版本"类问题以当日语料为准。
