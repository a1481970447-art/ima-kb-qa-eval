## 二、跑批设计

### 2.1 执行参数
| 项 | 值 | 说明 |
|---|---|---|
| 评测集 | 50 条（fact 20 / reasoning 15 / refusal 10 / multi_doc 5） | D2 产出，金标 100% 可溯源 |
| 生成模型 | hy3（temperature=0.2） | 与 D3/D4 一致 |
| 检索 | top-k=8，命中口径分 top-k 全量 / top-3 两档 | rank 4-8 的"命中"记为弱命中 |
| 裁判 | hy3 独立 judge prompt，temperature=0.7，每指标 3 次取多数 | 与 D4 验收配置一致 |
| 裁判并发 | 4 workers（每指标 3 次并行） | 单题耗时从 ~95s 降至 ~50s |
| 健壮性 | chat 调用 3 次指数退避重试；parse_error 補跑；整题 3 次重试；每题完成即写 checkpoint | 断点续跑，不重复计费 |

### 2.2 错误判定（fatal）口径
一条题被判"错误"（进入归因池）当且仅当：
- **拒答题**：`refusal_accuracy == False`（应拒答却乱答，或话术口径错误）
- **非拒答题**：满足以下任一
  - `factuality == incorrect`（关键事实与金标矛盾）
  - `faithfulness == unsupported`（大量论断无检索依据）
  - `completeness == missing`（金标要点基本未覆盖）
  - 错误拒答（该答却拒答）

`partial` 判定**不进**错误池（记为弱问题），但全部进入人工复核清单——避免把"不够精确"夸大成"错误"，保证归因结论的保守性。

## 三、三层自动归因决策树（D5 核心）

```
错误样本
├── A. 拒答题应拒答未拒答 ──────────────→ 【生成层】拒答边界执行失败
│        （陷阱文档高位召回记为诱因备注，属检索+数据复合）
├── B. 非拒答题
│   ├── B1. 错误拒答
│   │     ├── 金标在 top-3 ──────────→ 【生成层】有据可答仍拒答
│   │     └── 金标未进 top-3 ─────────→ 【检索层】无据可答而拒答
│   ├── B2. 金标未进 top-3
│   │     ├── rank 4-8（弱命中）──────→ 【检索层】排序问题
│   │     └── 未召回 ────────────────→ 【检索层】切块/召回问题
│   ├── B3. multi_doc 金标未全部进 top-3 → 【检索层】部分召回
│   └── B4. 金标在 top-3，答案错误
│         ├── 数据层信号命中 ──────────→ 【数据层】库内容脏/冲突
│         └── 无数据层信号 ───────────→ 【生成层】编造/误读/要点丢失
```

### 数据层信号的自动判据（两条，命中其一即归数据层）
1. **忠实度-正确性交叉**：`faithfulness == supported 且 factuality == incorrect`
   —— 回答忠实于检索上下文，但与金标矛盾 ⇒ 上下文本身是错的（脏数据污染排序）。
   这是 RAGAS faithfulness 指标的反向应用（D14）。
2. **陷阱文档召回**：eval_set 的 `trap_note` 中标注的数据层埋点文档（D08 过期帖、D10 旧清单、D05 旧评测等）出现在检索结果且事实错误。

### 为什么这个三分法是"纯 PM 视角"
| 归因层 | 技术解法 | 产品解法（ima 可落地动作） |
|---|---|---|
| 检索层 | 优化切块/重排 | 引导用户调整文档结构（标题层级） |
| 生成层 | 调 prompt/模型 | badcase 反馈闭环 |
| **数据层** | —— | **知识库健康度：冲突检测、过期提醒、信源权威度标注** |

数据层错误无法靠调模型解决，只能靠产品机制让用户治理知识库——这是只有 PM 会得出的归因结论，也是本 demo 的 punchline。

## 四、跑批统计结果

**执行**：50/50 条全量完成，耗时 23.9 分钟，0 条失败（checkpoint 断点续跑机制全程未启用——一次跑通）。

### 4.1 总分与分层
| 指标 | 结果 | 口径 |
|---|---|---|
| 总体错误率 | **18%（9/50）** | fatal 口径（见 2.2），partial 不计入 |
| 检索命中率（top-3） | 87.5%（35/40） | 非拒答题，文档级 |
| 拒答准确率 | **100%（10/10）** | 10 条库外问题全部正确拒答 |
| 事实正确率 | 67.6% correct / 14.7% partial | 裁判 majority（跑了 factuality 的题） |
| 引用忠实度 | 100% supported | 无编造型回答 |
| 完整性 | 41.2% complete | 弱项：要点覆盖不足是普遍问题 |
| 平均端到端延迟 | 14.87s | 检索+生成 |

分题型错误率：fact 15%（3/20）｜ reasoning 20%（3/15）｜ refusal **0%**（0/10）｜ **multi_doc 60%**（3/5）——多文档关联是最弱环节，与 D1 痛点笔记预判一致。

## 五、人工复核与仲裁

### 5.1 复核范围
`d5_review_list.csv` 导出 11 条（裁判分歧 4 条 + partial 弱问题 + 数据层判定 + 检索/生成边界），叠加 9 条错误样本全量复核。

### 5.2 裁判分歧仲裁（5 处指标实例，majority 全部采信）
| 样本.指标 | 三次判定 | 仲裁 |
|---|---|---|
| F-15.factuality | partial/correct/correct | 采信 correct，记弱问题 |
| R-02.factuality | correct/partial/partial | 采信 partial，记弱问题 |
| R-02.completeness | complete/complete/partial | 采信 complete |
| R-12.factuality | incorrect/partial/partial | 采信 partial |
| R-13.faithfulness | partial/supported/supported | 采信 supported |

**结论：分歧率约 4%（5/约130 指标实例），majority 全部被采信、无一翻转——「3 次取多数」机制有效性得到直接验证**（对应 D4 验收标准的延续证据）。

### 5.3 两条改判的依据
1. **F-07（generation→retrieval）**：自动树的「错误拒答 + hit_top3 → generation」分支被文档级命中率误导——D02 命中的是无关章节，金标「模型切换+场景」章节并未召回。**方法论教训：文档级命中率会高估检索质量，需要章节级口径**（已写入 D6 看板需求）。
2. **M-04（retrieval→data）**：D10 过期表述 TOP1 高位命中且被模型采信为权威答案（数据层埋点在复现架构中真实触发）；权威清单未召回是次因、模型无信源权威度取舍能力是第三因。复合错误按主因判数据层。

### 5.4 关键发现（写进评测报告的四个洞察）
1. **数据层错误在复现架构中被低估**：仅 1/9，远低于 D1 在 ima 实测的体感。原因：数据层错误的爆发需要「过期文档高位排序 + 生成层采信」联合失败，复现 pipeline 恰好两点都与 ima 不同（向量分布、指令遵从）。M-04 证明机制可触发、频率被复现架构低估——**复现结论用于方法论演示，不构成对 ima 的定量指控**（对应方案第七节风险声明）。
2. **错误拒答是最大错误形态**（4/9）：拒答话术未区分「库内确实没有」（FP1）与「召回不足」——产品启示：反馈闭环应让用户区分这两种「没答案」，前者引导补文档，后者是检索 bug。
3. **R-04 是 FP4 Not Extracted 的自我复现**：用 Seven Failure Points 论文定义的失败点框架，诊断出了对该论文提问的同类失败——评测体系的自洽性彩蛋。
4. **M-01 揭示元数据隔离与信源身份的矛盾**：front-matter 剥离防住了元数据污染（D1 教训 A-14），却也剥掉了「腾讯云百科/搜狗百科」的词条出处，模型无法回答「两个词条的差异」——**知识库健康度设计必须同时考虑污染防护与信源可追溯**，这是纯 PM 视角的权衡洞察。
